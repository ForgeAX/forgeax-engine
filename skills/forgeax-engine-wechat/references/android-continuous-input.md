# Continuous Android gameplay input

Use [android_game_multitouch.py](../scripts/android_game_multitouch.py) for a
bounded ordinary-game walk/run/jump and continuous-look journey. It consumes the
same full-contact snapshot timeline as the browser runner, generated by
[timeline.mjs](../scripts/fixtures/gameplay-benchmark/timeline.mjs). It changes no
World state or rendering settings. Unlike sequential `adb shell input`, one
official scrcpy control socket retains independent native contacts.

## Prepare and run

1. Select the intended already-authorized phone and ordinary publication. Confirm
   the exact game is foregrounded; another app, account, or phone is not a retry
   target. The capture and manifest association records the selected publication;
   it does not independently attest the bytes running inside WeChat.
2. Make and review an [Android `--for-input` capture](android-device.md). Derive
   move/look/run/jump rectangles from that phone's current UI, in actual display
   pixels. Supply them to `createGameplayTimeline` with
   `coordinateSpace: {width, height, unit: 'device-px'}`. Do not reuse browser or
   simulator rectangles. Transfer the exact capture result, PNG, selected
   `forgeax-dist.json`, and generated timeline JSON to the ADB-owning machine.
3. Transfer this skill's `scripts/` directory to the same machine, retaining the
   Python imports. Use a private server cache and a new private output directory:

```sh
python3 /absolute/skill/scripts/android_game_multitouch.py \
  --adb /absolute/platform-tools/adb --serial SELECTED_SERIAL \
  --cache /absolute/private/scrcpy-cache \
  --capture-result /absolute/private/prepared/result.json \
  --screenshot /absolute/private/prepared/screen.png \
  --manifest /absolute/private/forgeax-dist.json \
  --timeline /absolute/private/phone-timeline.json \
  --out /absolute/private/new-input-run
```

Run on the machine that owns ADB: a forwarded socket's `127.0.0.1` is local to
that machine. No desktop scrcpy window, video, audio, APK, power change or clipboard
synchronization is started. The script reuses `scrcpy_handshake.control_session`
as the single owner of pinned server verification, unique SCID/JAR, forwarding,
connection and cleanup. See [official protocol and source](android-multitouch.md).

## Timeline and termination

`forgeax-gameplay-input/1` records full active-contact snapshots. Fixed IDs are
1 move, 2 look, 3 run, 4 jump. Omitted contacts receive UP; new contacts receive
DOWN; changed positions receive MOVE. Removing Run does not release Move. Input
must use integer coordinates inside the captured display, four ordered contiguous
phases (`walk`, `run`, `jump`, `run-jump`), at most 20000 snapshots and at most
120 seconds. The last snapshot releases all contacts at `durationMs`.

The manifest and PNG hashes must match the prepared capture, including its exact
display dimensions, rotation, serial, ActivityRecord, user, component, task and
PID. The same target is checked before connection setup and again immediately
before timing starts. During dispatch, one independent guard thread checks the
focused/unlocked target every 1000 ms after its previous sample completes. It
stops new actions on a changed/unknown target or a sample older than 2500 ms,
measured from the start of that sample. These snapshots narrow the race; they
are not an atomic ownership lease. A foreground or rotation change can occur
between checks. A stale or slow guard is a stopped run, not grounds to quietly
remove checks or substitute another device.

SIGINT/SIGTERM request cancellation. Between sends, cancellation/guard checks run
at most 20 ms apart while waiting; the control socket has a 250 ms send timeout.
An event more than 100 ms late stops the run instead of bursting accumulated
actions. These are bounds/policies, not measured phone input latency. CLI options
can adjust the explicitly recorded bounds when evidence warrants it.

Every healthy-transport exit attempts explicit UP for each held contact, including
guard failure and cancellation, before the session owner closes the socket. If a
send fails, it may have left a partial 32-byte message: sending another packet
could corrupt framing. The driver stops using that stream and records
`releaseStatus: unknown` with `unreleasedPointerIds`. It never reconnects/replays
input or substitutes ACTION_CANCEL. Inspect the actual game's contact state
before another journey; a closed socket alone does not prove release.

## Read the result

The private `result.json` binds capture-result, PNG, selected manifest and timeline
hashes; stdout contains only state, whether input was attempted, and artifact path.
`session.execution` records phase boundaries, the dispatch clock origin, dispatched
events/messages, send-call cost, event lateness (mean/p95/p99/max), and release
evidence. `guard` separately records sample spans/cost, freshness policy and thread
shutdown. The callback timing origin is after startup and the second preflight;
do not charge server setup or ADB guard cost to socket dispatch.

`state: dispatched` means the schedule reached the socket and owned cleanup
completed. `up-messages-dispatched` is also only transport evidence: scrcpy has no
per-touch acknowledgement. Neither state qualifies game behavior, actual contact
release, frame rate, or input-to-photon latency. Pair the input receipt with the
ordinary game's native observation callback and complete-scene GPU completion
intervals. Guard work still adds real CPU/device load even though it is measured
separately; report it when interpreting a performance run. Match the publication
identity and phase window, then inspect movement/Run/jump/look consequences before
claiming a phone journey pass.

Offline regression covers the official 32-byte touch layout through a local
socket pair, four independent lifetimes, releasing Run while Move stays held,
shared JavaScript timeline generation, bounds/source checks before device work,
foreground/rotation/staleness/cancel stops, explicit releases, unknown partial
transport failure, and cleanup isolation. These tests are not native Android
gameplay qualification.
