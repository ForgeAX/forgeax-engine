# WeChat Worker execution

Use this reference before proposing Workers for the ordinary game or interpreting
a Browser benchmark as a threaded run. The current generated WeChat game keeps
App, World and Renderer in the main game realm. Worker V2 describes additional
native capabilities, but needs target admission and Engine integration.

## Current Engine path

Source inspected on **2026-10-13**, against Engine
[`39495a68109e234eb00693019c7eceb9d7e951d2`](https://github.com/ForgeaX-Games/forgeax-engine/tree/39495a68109e234eb00693019c7eceb9d7e951d2):

- [DevKit's WeChat producer](../../../packages/devkit/src/build/wechat.ts)
  constructs the native Renderer, World, UI and services before calling the local
  object-form `createApp({ platform, renderer, world, ... })`.
- [Local App assembly](../../../packages/app/src/app-assembly.ts) reports
  `unavailableExecutionCapabilities('local assembly')`, `engine: false` and the
  Host realm. The [platform contract](../../../packages/platform-wechat/README.md#execution-scope)
  has no WeChat Worker, Worker V2 or open-data-domain entry/transport.
- The [Browser gameplay fixture](gameplay-performance.md) reuses the generated
  WeChat entry. Both that fixture and the ordinary game therefore have Engine and
  Render Workers disabled. Browser App's separate execution entry supports
  Workers; that does not enable them in these workloads.

The Engine observations above are a source review. The separate physical-phone
probe below reached the V2 admission guard only; neither result qualifies a
threaded game or its FPS.

## Physical-phone admission evidence

On **2026-10-13 at 09:17:53.653 UTC**, an owned Android phone running
**WeChat 8.0.79 / SDK 3.17.4** returned Boolean
`wx.env.isSupportStandardWorker === false`. The producing session identified
Android 16; the original report itself records the Android platform, not the OS
release. The original report, receipt, image and probe-source hashes
retain `v2-not-admitted`, zero created Workers and no errors.

This device/AppID/base-library combination was not admitted for that run. It does
not establish lack of V2 support across WeChat or identify which rollout condition
caused the false flag. The probe deliberately stopped before Worker creation;
Worker execution, transfer, canvas, shared memory and WASM remained untested.
The screenshot's WeChat `RT-FPS 63` / `EX-FPS 0` overlay is not Engine FPS.

The maintained tools below improve error handling, cleanup and report identity.
Their generated bytes differ from that one-off probe. Offline checks exercise
both branches with native API substitutes and actual loopback HTTP, but the
maintained admitted branch has **not** been qualified on a physical phone.

## Official classic Worker and V2 contracts

The following official pages were retrieved on **2026-10-13**. The
[Worker V2 page](https://developers.weixin.qq.com/minigame/dev/guide/base-ability/new-worker)
lists **2026-08-10** as its document-change date and states (English translation):

> Worker V2 is still in staged rollout. Confirm the base-library and client
> versions, and rollout admission before use.
>
> Android: client >=8.0.74, base library >=3.17.0.
>
> iOS: support is under development.
>
> DevTools does not yet support the new multithreading capability.

Its capability flag is `wx.env.isSupportStandardWorker`. Record the actual flag,
client/base-library versions and gray-release admission on the selected target.
Meeting version minima alone does not establish admission. Under this dated
official contract, **Worker V2 is unavailable for the current DevTools simulator
performance task**; an admitted Android target is a separate qualification path.

| Boundary | Classic Worker | Worker V2 |
| --- | --- | --- |
| Rendering | The guide states that Workers have no rendering capability. | Documents OffscreenCanvas transfer; the example draws with a `2d` context and Worker `requestAnimationFrame`. |
| Concurrency | The guide limits concurrent Workers to one and does not support messages between Workers. | Documents multiple Workers; nested creation and transferable MessagePort are not established by this page. |
| Data | Guide describes copied messages. The `postMessage` API page documents arbitrary data after base library 2.20.2, but no transfer-list parameter. | Shows an OffscreenCanvas transfer list and SharedArrayBuffer. Those examples do not prove every transferable or `Atomics.wait`. |
| Native APIs | The guide excludes `wx` APIs from Workers. | Selected audio/network APIs use the `worker` object, not `wx`. This does not establish filesystem or WASM API availability. |
| Packaging | `game.json.workers` names the code root; scripts use `require` within it. | Retains the root restriction: only JS inside the Worker directory; other static files stay outside. |

Classic authorities: [Worker guide](https://developers.weixin.qq.com/minigame/dev/guide/base-ability/workers.html),
[`Worker.postMessage`](https://developers.weixin.qq.com/minigame/dev/api/worker/Worker.postMessage.html),
and [`wx.createWorker`](https://developers.weixin.qq.com/minigame/dev/api/worker/wx.createWorker.html).
Do not apply their classic restrictions to V2. The `useExperimentalWorker: true`
option documented by `wx.createWorker` improves iOS JS execution and may require
`onProcessKilled` recovery; it is not the V2 admission flag.

The [`wx.createCanvas` contract](https://developers.weixin.qq.com/minigame/dev/api/render/canvas/wx.createCanvas.html)
says the first call creates the on-screen canvas; later calls create offscreen canvases.
An ordinary offscreen canvas alone does not establish transfer semantics. V2
explicitly shows transferring the existing main canvas:

```js
const canvas = wx.createCanvas();
const offscreenCanvas = canvas.transferControlToOffscreen();
const worker = wx.createWorker('workers/render-worker/index.js');
worker.postMessage({ type: 'init-canvas', canvas: offscreenCanvas }, [offscreenCanvas]);
```

After transfer, the main thread must stop drawing through that canvas's context.
The V2 page also warns against `buffer instanceof SharedArrayBuffer` and uses
`buffer?.constructor?.name === 'SharedArrayBuffer'` for that native check. Its
examples establish neither Worker WebGL2 nor the selected wgpu WASM's successful
initialization, and do not establish Worker `navigator.gpu`, package-file access,
`WXWebAssembly`, nested Worker creation or display-canvas recovery after termination.

## Build and retrieve a bounded capability probe

Use [build_worker_probe.mjs](../scripts/build_worker_probe.mjs) for an owned,
disposable Mini Game. It bundles separate main/Worker entries, reuses the existing
phone report hash/receipt transport, and writes a manifest of all generated bytes.
It needs the selected Engine checkout's installed build dependencies; no Engine,
WASM or asset build is performed. Output must be a new private directory.

```sh
node skills/forgeax-engine-wechat/scripts/build_worker_probe.mjs \
  --engine-root /path/to/engine-with-dependencies \
  --out /private/new-worker-probe --run-id worker-check-unique \
  --appid "$LOCAL_APPID" --report-url http://127.0.0.1:19145/worker-report

node skills/forgeax-engine-wechat/scripts/receive_worker_report.mjs \
  --publication /private/new-worker-probe --out /private/new-worker-result \
  --report-url http://127.0.0.1:19145/worker-report --deadline-ms 180000
```

Use the already authorized AppID and the [physical-phone preview route](android-device.md).
On the selected ADB machine, an explicit
`adb -s DEVICE_SERIAL reverse tcp:19145 tcp:19145` connects the phone's loopback
to the receiver on that machine; remove that owned reverse after collection.
If the receiver runs elsewhere, first provide an owned forward between those
machines. Neither helper opens DevTools, uploads, selects a phone or installs
forwarding. Without `--report-url`, the probe only saves its report privately
through the native filesystem and logs its summary.

The probe records the actual admission flag/type and realm globals. A false or
missing flag ends with `v2-not-admitted` and no Worker creation. If admitted, it
attempts two packaged Workers, records the sender buffer after transfer and each
receiver's bytes, observes shared access only when Atomics is present, and transfers
the first display canvas only when its native transfer method exists. Worker 0
attempts WebGL2 clears/readback; available rAF produces at most 60 callbacks,
otherwise one clear. These are primitive capability observations, **not 60
completed Renderer frames or performance acceptance**. Missing capabilities remain
separate fields. `two-workers-replied` does not imply that every capability passed.
The default 20-second deadline is configurable from 1 to 60 seconds; errors,
Worker kills and timeout retain their cause and terminate already-created Workers.

The receiver accepts one report at the explicit loopback path, within 64 KiB and
a 0.1-600 second collection deadline. It verifies the publication bytes before
listening, then checks report length/hash, run ID, entry identities and terminal
shape. Wrong endpoint requests are rejected; the first candidate report either
saves or ends in a rejection. It writes original `report.json` plus a `receipt.json`
and closes owned connections. `saved` acknowledges report storage, not Worker or
rendering success. It has its own Worker report kind; the existing startup/GL
receiver remains unchanged.

Retain the generated manifest with the report and screenshot. AppID, device serial,
endpoint and `project.config.json` stay private. Publish sanitized evidence with
actual source hashes; never assign later tool revisions to an earlier run.

For the maintained tool's offline behavior checks:

```sh
node --test skills/forgeax-engine-wechat/scripts/__tests__/worker-probe.test.mjs
```

`FORGEAX_WORKER_TEST_ENGINE_ROOT` can select an existing checkout with dependencies
when testing from a source-only worktree. The suite checks generated identities,
false admission, transfer observations, exceptions/termination, missing Atomics,
clear/readback counters and real loopback acceptance/rejection/deadlines. It uses
no browser, simulator or physical device.

## Engine boundaries that need native adaptation

Reuse [App's existing execution owners](../../../packages/app/README.md),
Host/Engine and RenderWorker protocols, source publications, mesh residency,
frame credits and lifecycle identities. DevKit's plugin programs/Bootstrap/Catalog
and the native RHI initializer remain the assembly owners. A second World,
publication registry or Worker scheduler would duplicate those responsibilities.

| Owner | Current assumption and native work |
| --- | --- |
| [Capability probe](../../../packages/app/src/execution/capabilities.ts) and [selector](../../../packages/app/src/execution/selector.ts) | Engine and Render require `worker`, `offscreenCanvas` and `workerWebGpu`; Render also requires Engine enabled. Browser probes use Blob URLs and Worker `navigator.gpu`. Native WebGL/WASM cannot be admitted by setting `workerWebGpu: true`. Kernels additionally require `crossOriginIsolated`, SAB and `atomicsWait`; keep them disabled until independently qualified. |
| [Worker entry](../../../packages/app/src/execution/engine-worker.ts) and [runtime](../../../packages/app/src/execution/engine-worker-runtime.ts) | Browser module URLs, global `postMessage`, message events with `.data` and `close` need native packaged-path, `worker.onMessage` and termination bindings. The [WeChat RealmMessageChannel](../../../packages/platform-wechat/src/message-channel.ts) stays in one realm and rejects transfer lists; it cannot supply cross-thread transport. |
| [WeChat build](../../../packages/devkit/src/build/wechat.ts) and [WASM host](../../../packages/platform-wechat/src/wasm.ts) | Generate each realm's JS closure and Worker configuration; instantiate the selected native RHI in the GPU-owning realm using `NativeWgpuHost` / `initializeNativeWgpu` and `constructRuntimeRendererHost`. The current bootstrap has no native WeChat RHI initializer hook, and Worker equivalents of the Host's wx filesystem / `WXWebAssembly.instantiate(packagePath, imports)` remain unverified. |
| [Split Render creation](../../../packages/app/src/execution/source-render-worker.ts) and [Host recovery](../../../packages/app/src/execution/host-controller.ts) | Render Worker is currently created inside Engine Worker. Recovery clones/replaces an HTML canvas and transfers it again. Native nested creation, canvas handoff and display-canvas recovery each need a demonstrated lifecycle. |
| [Native UI assembly](../../../packages/devkit/src/build/wechat.ts) | Renderer calls the realm-local `ui.paintGpu`; Blitz document and input ownership remain live objects. Worker bootstrap has no WeChat UI-paint transport. Establish that ownership and resource path without cloning callbacks/native handles; 3D output alone cannot qualify the complete game. |

## Minimum qualification path

1. **Admit the target.** Keep the current official simulator on local execution.
   For a separate Android candidate, record versions, gray admission and the actual
   V2 flag. Retain unsupported results and stop that candidate's Worker path.
2. **Qualify one packaged Worker.** In an owned disposable project, check message
   order, errors, termination and actual ArrayBuffer transfer semantics. Report
   rAF, WebGL2, MessagePort transfer, SAB/Atomics and WASM/package access separately.
   A successful `postMessage` call alone does not prove transfer. Keep kernels off.
3. **Qualify the same native RHI.** Transfer the owned display canvas, initialize
   the exact selected wgpu payload inside the Worker, and retain nonzero pixels,
   60 actual completed frames, native completion and disposal evidence. This
   establishes capability only, without changing the App cap or rendering quality.
4. **Integrate existing App protocols.** Start with Engine and Renderer together
   in one Worker; split Render only after creation/handoff capabilities pass.
   Classic “World in Worker, Renderer on main” is a new current-App topology,
   not an existing switch.
5. **Qualify the ordinary game.** Reuse the same publication, quality, configured
   cap and input workload (cap 2 in the current gameplay baseline). Preserve GPU
   UI, touch/keyboard/audio and hide/show, resize, recovery and termination behavior;
   then compare [actual App completions](gameplay-performance.md).

Moving JS changes scheduling; it does not by itself resolve GPU/driver completion
delays. Worker availability or rAF rate is not an FPS pass. Browser WebGPU Worker
results change the backend and cannot replace WeChat's native WebGL acceptance.
